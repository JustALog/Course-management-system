% =========================== 1. INTRODUCTION ===========================
\section{Introduction}

Every semester, thousands of university students rush to register for their
courses at the same moment the registration window opens. Anyone who has gone
through this knows how stressful it can be: classes fill up within minutes,
timetables clash, and it is often unclear whether a registration actually went
through. On the other side, the academic office has to manage courses,
semesters, class sections and rooms, frequently with spreadsheets and manual
checks.

In this report, I describe a project that I have worked on to address this
problem: the \textbf{Course Management \& Registration System}. It is a
full-stack web application with two portals, one for \emph{students} and one
for \emph{administrators}. Students can browse open class sections, register
or cancel, see their weekly timetable and look up their grades.
Administrators can manage courses, semesters, class sections and schedules, and
monitor registrations in real time.


% =========================== 2. BACKGROUND ===========================
\section{Background and Motivation}
\label{sec:background}

\subsection{The problem}
Course registration looks simple, but it hides several hard problems:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Capacity:} each class section has a fixed number of seats, and
        many students may try to take the last seat at the same time.
  \item \textbf{Timetable conflicts:} a student must not register for two
        sections that meet at the same time.
  \item \textbf{Time windows:} registration and cancellation are only allowed
        during a period set by the academic office.
  \item \textbf{Account status:} suspended students must not be able to register.
  \item \textbf{Traceability:} cancelled registrations should be kept for
        auditing instead of being deleted.
\end{itemize}

\subsection{Objectives}
My objectives for the project were to:
\begin{enumerate}[leftmargin=1.5em]
  \item build a working web application with separate student and admin portals;
  \item enforce all registration rules on the server so that the data always
        stays consistent, even under concurrent requests;
  \item design a clean, normalised relational database;
  \item make the system easy to deploy with a single command using Docker;
  \item practise professional development habits: a layered architecture,
        documentation and version control with Git.
\end{enumerate}

\subsection{Architecture}

The project is organised as a \textbf{monorepo} with two workspaces,
\texttt{client} and \texttt{server}. The backend follows a layered
architecture, where each layer has a single responsibility
(Figure~\ref{fig:arch}):

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Routes} map URLs such as \texttt{POST /api/enrollments} to controllers.
  \item \textbf{Middleware} handles authentication (JWT), authorisation
        (student/admin roles), input validation and errors.
  \item \textbf{Controllers} read the request and send the response.
  \item \textbf{Services} contain the business logic, for example the
        enrollment and schedule-conflict rules.
  \item \textbf{Models} (Sequelize) map JavaScript objects to MySQL tables.
\end{itemize}

Important rules are also enforced inside the database, as a second line of
defence:
\begin{itemize}[leftmargin=1.5em]
  \item a \textbf{unique index} on \texttt{(student\_id, section\_id)} in
        \texttt{enrollments} prevents duplicate registrations;
  \item a \textbf{CHECK constraint} guarantees
        \texttt{current\_students <= max\_students};
  \item scores must be between 0 and 10, and \texttt{day\_of\_week} must be valid;
  \item indexes on foreign keys and status columns keep common queries fast.
\end{itemize}

\section{Registration Business Rules}
\label{sec:rules}

The heart of the project is the enrollment service. I wrote down nine business

\midrule
BR01 & A student cannot register for the same section twice. \\
BR02 & Registration is refused when the section is full. \\
BR03 & Registration is only allowed inside the semester's registration window. \\
BR04 & The system detects and blocks timetable conflicts. \\
BR05 & Suspended students cannot register. \\
BR06 & Closed or cancelled sections cannot be registered. \\
BR07 & Cancellation is only allowed inside the registration window. \\
BR08 & The section's student counter decreases automatically on cancellation. \\

\caption{Business rules for registration and cancellation}
\end{table}

\subsection{Preventing race conditions}
The most difficult rule was BR02. If two students try to take the last seat at
the same moment, a naive implementation reads ``1 seat left'' for both and
registers both, so the class becomes over-full. To prevent this, the whole
registration runs inside a \textbf{database transaction}, and the section row
is locked with \texttt{SELECT \ldots{} FOR UPDATE}. The second request has to
wait until the first one commits, and then it sees that the section is full.

\begin{lstlisting}
const transaction = await sequelize.transaction();
try {
  // Row-level lock: other requests for this section must wait
  const section = await Section.findByPk(sectionId, {
    include: [{ model: Semester, as: 'semester' }],
    lock: transaction.LOCK.UPDATE,
    transaction,
  });
  if (section.current_students >= section.max_students) {
    throw ApiError.badRequest('Section is full');          // BR02
  }
  // ... BR01, BR03-BR06 checks ...
  await Enrollment.create({ student_id, section_id, status: 'enrolled' }, { transaction });
  await Section.increment('current_students', { by: 1, where: { section_id }, transaction });
  await transaction.commit();
} catch (error) {
  await transaction.rollback();                             // all-or-nothing
  throw error;
}
\end{lstlisting}

\subsection{Detecting timetable conflicts}
For BR04, the schedule service compares every meeting time of the new section
with the meeting times of all sections the student is already enrolled in for
the same semester. Two meetings conflict when they are on the same day, their
period ranges overlap, and their week types are compatible (a class held only
in odd weeks never clashes with one held only in even weeks):

\begin{lstlisting}
_isConflict(a, b) {
  if (a.day_of_week !== b.day_of_week) return false;
  // [startA, endA] ∩ [startB, endB] ≠ ∅
  const overlap = a.start_period <= b.end_period && a.end_period >= b.start_period;
  if (!overlap) return false;
  if (a.week_type === 'odd'  && b.week_type === 'even') return false;
  if (a.week_type === 'even' && b.week_type === 'odd')  return false;
  return true;
}
\end{lstlisting}

When a conflict is found, the API returns HTTP \texttt{409 Conflict} together
with the details of the clashing section, so the student knows exactly which
class to change.

% =========================== 6. PROCESS ===========================
\section{Development Process}
\label{sec:process}

I developed the project between January and March 2026 and used Git
throughout. The work went through five main stages:

\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Analysis (January).} I studied how registration works at my
        university, listed the features for each type of user and wrote the
        nine business rules.
  \item \textbf{Database and backend (March).} I designed the eight-table
        schema, wrote the SQL migration and seed data, and implemented the
        Express API: authentication, courses, semesters, sections, schedules,
        enrollments and results.
  \item \textbf{Restructuring.} When the project grew, I reorganised it into a
        monorepo with \texttt{client} and \texttt{server} workspaces, so both
        can be started with one command (\texttt{npm run dev}).
  \item \textbf{Frontend.} I built the student site and the admin site in
        React, then refined the UI and added dark mode.
  \item \textbf{Deployment and documentation.} I added Dockerfiles and a
        Docker Compose file that starts MySQL, the API and the Nginx frontend
        together, with health checks. I also wrote documentation for the
        backend API, the database and Docker deployment.
\end{enumerate}

% =========================== 8. LESSONS ===========================
\section{What I Learned}
\label{sec:lessons}

This project taught me much more than any single course exercise:

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Technical skills.} I became confident with React, Express,
        Sequelize and MySQL, and I now understand why transactions and locks
        matter in real systems.
  \item \textbf{Thinking before coding.} Writing the business rules first made
        the implementation much clearer, and each rule maps to a few lines of
        code that are easy to find.
  \item \textbf{Clean architecture.} Separating routes, controllers, services
        and models made it easy to change one part without breaking others.
  \item \textbf{Professional habits.} Using Git, writing documentation and
        containerising the application are habits I will keep in future
        projects.
\end{itemize}

\subsection{Future improvements}
Next, I would like to enforce course prerequisites automatically, add a full
automated test suite with Jest, offer a waiting list with email notifications
for full sections, and add caching and wider rate limiting (today only the
login route is limited) to handle the peak load when registration opens.

% =========================== 9. CONCLUSION ===========================
\section{Conclusion}

The Course Management \& Registration System is the project I am most proud
of so far. It solves a real problem that every student experiences, and it
works from end to end: from the React interface, through a secure Express API,
to a carefully designed MySQL database, all packaged with Docker. Most
importantly, building it taught me how to turn a set of real-world rules into
reliable software, and how to organise a project so that it can keep growing.
